# 亚博 K230 红绿蓝木块识别

K230 负责“看见”并输出三色木块的像素坐标，STM32F103C8T6 负责“决策”并驱动机械臂。
摄像头与云台加固在机械臂上（一体式），会随机械臂一起运动。

## 目录内容

| 文件 | 作用 | 什么时候跑 |
| --- | --- | --- |
| `01_camera_check.py` | 相机自检，只出画面和板卡信息 | 换线、换板、画面异常时 |
| `03_auto_calibrate.py` | **自动标定三色阈值**（背景差分法） | 每次换木块、换环境光都要跑 |
| `02_color_uart.py` | 识别主程序，画框 + 串口发三色全景帧 | 日常运行 |
| `04_servo_probe.py` | 云台舵机 PWM 引脚探测 | 暂缓，等硬件确认 |
| `05_scan_color.py` | 云台扫描找木块 | 暂缓，等硬件确认 |
| `PROTOCOL_通信协议.md` | 给队友看的完整通信规范 | 联调前必读 |
| `stm32/` | STM32 侧协议解析模块（.c/.h） | 加进 Keil 工程 |

三个 Python 脚本互相独立，分别运行，不需要同时跑，也不需要电脑装 pip 包。

## 快速开始（三步）

1. **`01_camera_check.py`** —— 确认能看到实时画面，终端打印 `Camera OK`。
2. **`03_auto_calibrate.py`** —— 按屏幕提示依次放入红、绿、蓝木块，得到六元阈值。
   把输出的三行阈值粘进 `02_color_uart.py` 的 `COLOR_THRESHOLDS`。
3. **`02_color_uart.py`** —— 跑识别，看屏幕三色状态栏。

> 第 2 步不能跳。文件里自带的阈值只是试运行起点，不是你的木块的真实颜色。
> 阈值不换，识别精度就上不去，后面调什么都白费。

## 1. 相机自检 `01_camera_check.py`

1. 用可传数据的 USB 线连接 K230 与电脑，打开 CanMV IDE K230，点左下角连接。
2. 打开 `01_camera_check.py`，点运行。
3. 正常时 IDE 帧缓冲窗口显示实时画面，终端打印板卡、固件信息和 `Camera OK`。
4. 默认只显示到电脑 IDE，板载屏幕没画面不代表失败。

失败时保留终端完整报错和 `Board:` / `Python:` 输出，不要盲目刷别的固件。

**已知现象**：点“连接”后 IDE 会自动打开一个设备文件浏览窗口（能看板子里的文件），这是 CanMV IDE 的正常行为，不是 Windows 弹 U 盘。

**已知问题**：如果脚本崩溃退出，`Display.show_image()` 就不再被调用，屏幕会停在最后一帧或黑屏。
`03_auto_calibrate.py` 已经做了崩溃保护（异常画红底白字到屏幕上），`02` 还没有 —— 如果 `02` 黑屏，
先看 IDE 终端里的报错。

## 2. 阈值标定 `03_auto_calibrate.py`

### 为什么不能手动拖滑块

Codex 原来那版是“框一块区域 → 把整个框里的像素统计一遍”。木块只占框的 25% 时，
剩下 75% 的背景全混进去了。仿真量化对比过：

| 版本 | A 通道阈值跨度 | 后果 |
| --- | --- | --- |
| 旧版（整框统计） | `-45 .. 69`（跨度 114） | 几乎覆盖整个 A 空间，没有区分能力 |
| 新版（背景差分） | `39 .. 57`（跨度 18） | 只框住木块本身 |

这就是“怎么调都不对”的根源 —— 不是参数没调好，是取样方式错了。

### 新方法怎么做的

1. 从采样框**左右两侧**取背景像素，求**中位数**（不是均值，抗木块边缘干扰）。
2. 用 `find_blobs(invert=True)` 反选 —— 找“不是背景”的连通块，那就是木块。
3. 对木块外接矩形**向内收缩**后再统计，只取木块内部，边缘过渡带扔掉。
4. 多帧统计取中位数汇总。
5. 用 `mean ± 2.6σ` 算出六元阈值。

### 怎么跑

1. 把木块放在实际工作位置，保持照明稳定，跑起来。
2. 屏幕先倒计时，然后提示放入某色木块 —— 手动换块。
3. 依次走完红、绿、蓝（只想标一种就改文件头的 `ONLY_COLOR`）。
4. 屏幕显示结果，同时终端打印可直接粘贴的元组。
5. 把三行粘进 `02_color_uart.py` 的 `COLOR_THRESHOLDS`。

### 调参口诀

| 现象 | 改哪个参数 |
| --- | --- |
| 找不到木块 | `BG_TOL_L` / `BG_TOL_AB` 调**大** |
| 背景被当成木块 | `BG_TOL_L` / `BG_TOL_AB` 调**小** |
| 阈值框太大（容易串色） | `SIGMA` 从 2.6 降到 2.0 |
| 阈值框太小（框不住木块） | `SIGMA` 从 2.6 升到 3.2 |

### 编码自适应

不同固件版本下 LAB 的取值范围不一样（可能是 `0~255`，也可能是 `L:0~100 / A,B:-128~127`）。
脚本会自动判定，**判断顺序是先看 A/B 再看 L** —— 因为深灰桌面在 0~255 编码下 L≈102，
只看 L 会误判成标准编码。中性色的 A/B 在两种编码下差异最明显，所以以它为准。

标定完还会自检一次：如果算出来的阈值框不住木块，自动换另一组编码重算。

## 3. 识别主程序 `02_color_uart.py`

### 三色独立追踪

每色一个独立的 `StableTarget`，**只跟自己比**，取自己像素最大的块，不跨颜色比较。

跨颜色比较的后果（之前红蓝同时出现就失效的原因）：红蓝木块大小接近时，
像素数的正常波动会让“胜出者”每帧在红色和蓝色之间跳变，颜色 ID 一变稳定计数立刻清零，
永远攒不够帧数。仿真 200 帧对比（像素 4800~5200 随机波动）：

| 版本 | 有效输出帧 | 比例 |
| --- | --- | --- |
| 跨色比较（旧） | 1 / 200 | 0.5% |
| 每色独立（新） | 192 / 200 | 96.0% |

### 屏幕怎么看

- 左上角大字：`VALID: RED` 表示红色已成为稳定目标；`WAIT: no stable target` 表示还在攒帧。
- 三色状态栏（左中部）：

```text
RED    5120px  OK      ← 稳定，正在上报
GREEN   4980px  ..     ← 看到了，但还没稳定够帧数
BLUE      ---          ← 完全没看到
```

哪一色卡住了一眼就能看出来。

### 稳定判定条件

连续 ≥ 5 帧、持续 ≥ 250 ms、中心相对稳定窗口起点偏移 ≤ 12 像素。
目标丢失、位移过大或采集停顿超过 500 ms 后重新计数。

### 注意

这是**颜色分割**，不能判断材质是不是木头，也不能区分同色背景。
接触在一起的同色木块可能被当成一块。先用单块、干净背景验证。

## 4. 接线

### USB 不能直连

K230 和 STM32 都是 USB 从机，两个从机不能直连。必须走 UART 排针。

### K230 侧

亚博官方文档给出的 USB 旁通信口为 **UART1：GPIO9 = TX，GPIO10 = RX**。
这不是所有 K230 开发板的通用引脚，**请用实物丝印核对**，尤其确认该接口是否已被云台控制器占用
（一对 UART 不能同时接两个发送设备）。

### STM32 侧

| 方案 | 引脚 | 说明 |
| --- | --- | --- |
| **推荐** USART2 | PA2 = TX，PA3 = RX | 避开 PA9/PA10，不占用定时器通道 |
| 备选 USART1 | PA9 = TX，PA10 = RX | **PA9 同时是 TIM1_CH2**，如果 HTD-35H 总线舵机用了 PA9 就不能用 |

接线（本版 K230 只发不收，STM32 的 TX 可以暂不接）：

```text
K230 GPIO9 (TX)  ──────→  STM32 PA3 (USART2_RX)
K230 GPIO10 (RX) ←──────  STM32 PA2 (USART2_TX)   可暂不接
K230 GND         ───────  STM32 GND               必须共地
```

3.3 V TTL 逻辑。通信口的 5 V 电源脚**不是**串口信号线，不要接到 RX/TX 或 3.3 V。
两板各自有合适供电时不用互接电源。不能凭排线颜色判断针脚。

参数：**115200、8 数据位、无校验、1 停止位（8N1）**。

接好后把 `02_color_uart.py` 里的 `UART_ENABLED` 改成 `True`。

## 5. 通信协议

完整规范见 **`PROTOCOL_通信协议.md`**（含 C 实现、手算示例、故障对照表）。这里只给摘要。

三色全景帧，定长 13 字段：

```text
@T,seq,pan,tilt,rx,ry,rp,gx,gy,gp,bx,by,bp*XX\r\n
```

| 字段 | 含义 |
| --- | --- |
| `T` | 帧类型：三色全景观测帧 |
| `seq` | 0~65535，每次发送加一，回绕；重启从零开始 |
| `pan` / `tilt` | 云台当前角度（02 版固定视角，填死 90） |
| `rx,ry,rp` | 红块中心 x、中心 y、像素数 |
| `gx,gy,gp` | 绿块同上 |
| `bx,by,bp` | 蓝块同上 |
| `XX` | 两位十六进制 XOR 校验，范围是 `T` 到 `*` 之前的所有 ASCII 字节（含逗号） |

**某色没看到就填 `-1,-1,0`**，不沿用上一帧的旧坐标。

示例（每行实际带 CRLF）：

```text
@T,42,90,90,320,240,5120,180,260,4800,150,300,4300*52    三色都在
@T,42,90,90,320,240,5120,-1,-1,0,-1,-1,0*53              只有红
@T,42,90,90,-1,-1,0,-1,-1,0,-1,-1,0*62                   什么都没有
```

字段类型注意：像素数用 `uint32`，因为最大 640×480 = 307200，超过 `uint16` 上限 65535。

### 这是观测数据，不是指令

`seq` 是通信帧序号，不是木块编号。STM32 **不应**每收到一帧就启动一次抓取。
必须先按换行分帧、校验格式/校验和/字段范围，再更新内部状态。

UART 一次接收可能只有半帧，也可能有多帧粘在一起，**必须缓存拼帧**。
建议接收环形缓冲 ≥ 256 字节并处理溢出。

必须有**新鲜度超时**：500 ms 没收到合法帧就判定视觉离线，不能拿旧目标继续动。

## 6. 抓取决策三规则

规则在 STM32 侧实现，K230 只负责如实上报看到的一切。

1. **区域内只有一种颜色** → 直接夹它。
2. **有多种颜色** → 夹像素数最大的（像素数 ≈ 视野中占的面积，最大即最靠近 / 最正对）。
3. **分不出谁最大** → 按 **红 > 绿 > 蓝** 的顺序。

第 3 条的“分不出”用容差判定：最大值记为 `max_px`，
只要某色像素数 ≥ `max_px × 95%` 就算并列，并列时按红绿蓝顺序取第一个。

判定实例：

| 红 | 绿 | 蓝 | 结果 | 依据 |
| --- | --- | --- | --- | --- |
| 5120 | — | 4800 | 红 | 红最大 |
| 4000 | — | 6000 | 蓝 | 蓝最大 |
| 5120 | — | 5050 | 红 | 5050 ≥ 5120×95%=4864，算并列，按红绿蓝 |
| — | 5000 | 5000 | 绿 | 并列，绿在蓝前 |
| 5000 | 4950 | 4900 | 红 | 三者都在 4750 以上，全并列，取红 |
| 6000 | 4000 | 3000 | 红 | 只有红过线 |
| — | — | 4300 | 蓝 | 只有一种 |
| — | — | — | 无 | 全空，不动 |

容差比例在 `stm32/k230_protocol.h` 的 `K230_TIE_RATIO` 里，默认 95。
想更严格（更倾向选真最大的）就调高到 98；想更倾向红绿蓝顺序就调到 90。

| 文件 | 内容 |


## 8. 待确认的现场信息

1. K230 板子正反面、USB 旁通信接口和云台接线的清晰照片（确认 UART1 排针位置）。
2. 云台舵机信号线接的是 K230 还是 STM32 —— 决定扫描由谁驱动。
3. STM32 现有引脚占用：PA9 是否已被 HTD-35H 占用。
4. 机械臂用几个舵机、分别控制什么（底座旋转 / 大臂 / 小臂 / 夹爪）—— 才能写抓取状态机。
5. 木块尺寸、工作区范围、相机到桌面距离。
