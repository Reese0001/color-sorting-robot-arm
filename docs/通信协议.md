# K230 → STM32 通信协议

**版本** v1.0 · **日期** 2026-10-28 · **适用** 亚博 K230 云台款 ↔ STM32F103C8T6

---

## 0. 一句话说明

K230 每 100ms 发一帧 ASCII 文本，告诉 STM32「画面里红、绿、蓝三块木块各自在哪个像素位置」。
STM32 校验后解析，**自己决定抓哪一块**。

分工原则：**K230 只回答"看到什么"，不做决策。** 因为它不知道机械臂当前姿态、舵机有没有堵转、夹爪是不是已经夹着东西。

---

## 1. 物理连接

### 1.1 用 USART，不是 USB

K230 上那根 USB 线是接电脑跑 CanMV IDE 的调试通道，**和 STM32 无关**，数据到不了 STM32。
两个单片机之间必须走 **UART 排针 + 杜邦线**。

| K230 引脚 | 方向 | STM32F103C8T6 | 说明 |
|---|---|---|---|
| **GPIO9** (UART1_TX) | → | **PA3** (USART2_RX) | K230 发，STM32 收 |
| **GPIO10** (UART1_RX) | ← | **PA2** (USART2_TX) | 暂时可以只接单向，但建议接上 |
| **GND** | — | **GND** | **必接**，不接会乱码 |

### 1.2 三个必须注意的点

1. **不要用 PA9 / PA10（USART1）**
   PA9 已经被 HTD-35H 总线舵机的半双工信号线占用。如果机械臂不用总线舵机、PA9 空着，用 USART1 也可以，但要在两边同时改，别一边改一边不改。

2. **3.3V TTL 直连，不需要电平转换**
   K230 的 GPIO 是 3.3V，STM32 也耐受 3.3V。**不要**把 K230 的 5V 电源脚接到 STM32 的信号脚或 3.3V 脚。

3. **GND 必须共地**
   两块板各自有电源时，信号线必须有一根 GND 连着。漏了这根，现象是"数据全是乱码"或者"一个字节都收不到"，很容易误判成波特率问题。

### 1.3 串口参数

```
波特率    115200
数据位    8
校验位    无
停止位    1
流控      无
```

即 **115200 8N1**。

## 2. 帧格式

```
@T,seq,pan,tilt,rx,ry,rp,gx,gy,gp,bx,by,bp*XX\r\n
```

| 特征 | 说明 |
|---|---|
| 帧头 | `@`（0x40） |
| 帧尾 | `\r\n`（0x0D 0x0A） |
| 分隔符 | 英文逗号 `,` |
| 校验 | `*` 后跟两位**大写**十六进制 |
| 编码 | 纯 ASCII，无中文、无二进制 |
| 长度 | 不固定，随数字位数变化，典型 40~55 字节 |

## 3. 字段定义

| # | 字段 | 类型 | 有效范围 | 无效值 | 含义 |
|---|---|---|---|---|---|
| 1 | `T` | 字符 | 固定 `T` | — | 帧类型：Target 全景 |
| 2 | `seq` | uint16 | 0 ~ 65535 | — | 帧序号，每发一帧 +1，到 65535 后回到 0 |
| 3 | `pan` | uint8 | 0 ~ 180 | — | 云台水平角（度）。固定视角时恒为 90 |
| 4 | `tilt` | uint8 | 0 ~ 180 | — | 云台俯仰角（度）。固定视角时恒为 90 |
| 5 | `rx` | int16 | 0 ~ 639 | **-1** | 红色木块中心 x |
| 6 | `ry` | int16 | 0 ~ 479 | **-1** | 红色木块中心 y |
| 7 | `rp` | **uint32** | 1 ~ 307200 | **0** | 红色木块像素数 |
| 8 | `gx` | int16 | 0 ~ 639 | -1 | 绿色木块中心 x |
| 9 | `gy` | int16 | 0 ~ 479 | -1 | 绿色木块中心 y |
| 10 | `gp` | **uint32** | 1 ~ 307200 | 0 | 绿色木块像素数 |
| 11 | `bx` | int16 | 0 ~ 639 | -1 | 蓝色木块中心 x |
| 12 | `by` | int16 | 0 ~ 479 | -1 | 蓝色木块中心 y |
| 13 | `bp` | **uint32** | 1 ~ 307200 | 0 | 蓝色木块像素数 |
| 14 | `XX` | hex | 00 ~ FF | — | XOR 校验 |

### 坐标系

- 原点在画面**左上角**
- x 向右递增，y 向下递增
- 分辨率固定 **640 × 480**
- 坐标是**像素**，不是毫米。要换算成机械臂坐标必须另做标定，见第 8 节

### 无效值的含义

某色填 `-1,-1,0` 表示 **这一帧里没有看到该颜色的稳定目标**。
STM32 收到无效值时必须**丢弃该颜色的旧坐标**，不能沿用上一帧的位置。
否则木块被夹走后，机械臂还会往老地方扑空。

### 为什么每色只报一个

画面里同一颜色出现多块时，K230 只报**像素数最大的那一块**（通常是离镜头最近的）。
如果以后需要区分同色多块，协议要扩展，届时版本号会升级。

## 4. 校验算法

### 4.1 规则

对 `T` 到 `*` 之前的**所有 ASCII 字节**逐字节做异或（XOR）。

**参与校验**：`T` 以及所有字段、所有逗号
**不参与校验**：开头的 `@`、`*` 本身、两位校验字符、`\r\n`

### 4.2 C 实现

```c
static uint8_t k230_checksum(const char *body, uint16_t len)
{
    uint8_t x = 0;
    for (uint16_t i = 0; i < len; i++) {
        x ^= (uint8_t)body[i];
    }
    return x;
}
```

### 4.3 手工验算（拿这串对）

```
body = "T,42,90,90,320,240,5120,180,260,4800,150,300,4300"
```

按字节 XOR 结果为 **0x52**，所以完整帧是：

```
@T,42,90,90,320,240,5120,180,260,4800,150,300,4300*52\r\n
```

如果 STM32 解析这段算出来的不是 0x52，**校验代码写错了**，先修这个再谈别的。

## 6. STM32 侧接收流程

必须按这四层写，少一层都会出怪问题。

### 6.1 第一层：中断收字节进环形缓冲

**中断里只做一件事：把字节塞进缓冲区，立刻返回。** 不要在中断里解析字符串。

```c
#define RB_SIZE 256
static volatile uint8_t  rb[RB_SIZE];
static volatile uint16_t rb_head = 0, rb_tail = 0;

void USART2_IRQHandler(void)
{
    if (USART_GetITStatus(USART2, USART_IT_RXNE) != RESET) {
        uint8_t c = (uint8_t)USART_ReceiveData(USART2);
        uint16_t next = (rb_head + 1) % RB_SIZE;
        if (next != rb_tail) {          /* 满了就丢新字节，不覆盖旧数据 */
            rb[rb_head] = c;
            rb_head = next;
        }
        USART_ClearITPendingBit(USART2, USART_IT_RXNE);
    }
}
```

### 6.2 第二层：主循环拼帧

一次串口中断可能只收到半帧，也可能连着收到三帧。**必须缓存拼帧。**

```c
#define LINE_MAX 80
static char    line[LINE_MAX];
static uint8_t line_len = 0;
static uint8_t in_frame = 0;

void k230_poll(void)
{
    while (rb_tail != rb_head) {
        char c = (char)rb[rb_tail];
        rb_tail = (rb_tail + 1) % RB_SIZE;

        if (c == '@') {                 /* 帧头：无条件重来 */
            line_len = 0;
            in_frame = 1;
        } else if (in_frame) {
            if (c == '\n') {            /* 帧尾 */
                line[line_len] = '\0';
                k230_parse(line, line_len);
                in_frame = 0;
                line_len = 0;
            } else if (c != '\r') {
                if (line_len < LINE_MAX - 1) {
                    line[line_len++] = c;
                } else {                /* 超长：丢弃整帧，防止内存越界 */
                    in_frame = 0;
                    line_len = 0;
                }
            }
        }
    }
}
```

### 6.3 第三层：校验 + 分割字段

```c
static int8_t hex2(char c)
{
    if (c >= '0' && c <= '9') return c - '0';
    if (c >= 'A' && c <= 'F') return c - 'A' + 10;
    if (c >= 'a' && c <= 'f') return c - 'a' + 10;
    return -1;
}

void k230_parse(char *s, uint8_t len)
{
    char *star = strchr(s, '*');
    if (star == NULL) return;
    if ((uint8_t)(star - s) < 2) return;

    /* 校验：T 到 * 之前的所有字节 */
    uint8_t body_len = (uint8_t)(star - s);
    uint8_t calc = 0;
    for (uint8_t i = 0; i < body_len; i++) calc ^= (uint8_t)s[i];

    int8_t hi = hex2(star[1]);
    int8_t lo = hex2(star[2]);
    if (hi < 0 || lo < 0) return;
    if (calc != (uint8_t)((hi << 4) | lo)) return;   /* 校验失败，丢弃 */

    *star = '\0';

    /* 逗号分割，必须正好 13 个字段 */
    char   *f[13];
    uint8_t n = 0;
    char   *p = s;
    while (n < 13) {
        f[n++] = p;
        p = strchr(p, ',');
        if (p == NULL) break;
        *p++ = '\0';
    }
    if (n != 13) return;
    if (f[0][0] != 'T') return;

    /* 填进全局结构体 */
    vision.seq  = (uint16_t)atoi(f[1]);
    vision.pan  = (uint8_t)atoi(f[2]);
    vision.tilt = (uint8_t)atoi(f[3]);

    for (uint8_t i = 0; i < 3; i++) {
        int16_t cx = (int16_t)atoi(f[4 + i * 3]);
        int16_t cy = (int16_t)atoi(f[5 + i * 3]);
        uint32_t px = (uint32_t)atoi(f[6 + i * 3]);

        /* 范围检查：坐标越界视为无效 */
        if (cx < 0 || cx > 639 || cy < 0 || cy > 479 || px == 0) {
            vision.slot[i].valid = 0;
        } else {
            vision.slot[i].valid = 1;
            vision.slot[i].cx = cx;
            vision.slot[i].cy = cy;
            vision.slot[i].px = px;
        }
    }

    vision.last_rx_ms = millis();
    vision.frames_ok++;
}
```

### 6.4 第四层：新鲜度超时

**这一层最容易被忘掉，但最要命。**

```c
#define VISION_TIMEOUT_MS 500

uint8_t vision_online(void)
{
    return (millis() - vision.last_rx_ms) < VISION_TIMEOUT_MS;
}
```

K230 断电、脚本崩了、杜邦线松了——STM32 必须在 **500ms 内**察觉，并**禁止启动新的抓取**。
否则它会拿着几分钟前的坐标去抓空气，看起来像"机械臂抽风"。

## 7. 抓取决策（STM32 侧）

> **现成实现见 `firmware/lib/k230_protocol/k230_protocol.c` 的 `K230_PickTarget()`**，已通过 34 项单元测试。
> 下面只讲规则，代码直接用那个文件，不要自己重写。

### 7.1 选哪一块（三条规则，按顺序判断）

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 视觉掉线（500ms 内无合法帧） | 不抓 |
| 2 | 只有一种颜色有效 | **直接选它** |
| 3 | 多种颜色有效，某一色像素数明显最大 | **选像素数最大的** |
| 4 | 多种颜色有效，最大的几个差距在 5% 以内（分不出） | **按 红 > 绿 > 蓝 顺序选** |

**第 4 条为什么必须有**：两个木块大小接近时，像素数的正常波动会让"最大的那个"每帧跳变，机械臂就会左右摇摆、反复改主意。固定顺序能把这种抖动压住。

**"分不出"怎么算**：像素数 ≥ 最大值的 **95%** 就算并列。这个阈值是头文件里的 `K230_TIE_RATIO`，想更倾向选最大的就调到 99，想更容易触发颜色顺序就调到 90。

### 7.2 判定实例（照着核对）

| 红 | 绿 | 蓝 | 最大值 | 95% 线 | 结果 | 原因 |
|---|---|---|---|---|---|---|
| 5120 | - | - | 5120 | 4864 | **红** | 只有一种，规则 2 |
| 5120 | - | 4800 | 5120 | 4864 | **红** | 蓝 4800 < 4864，只有红达标 |
| 4000 | - | 6000 | 6000 | 5700 | **蓝** | 蓝明显最大，规则 3 |
| 5120 | - | 5050 | 5120 | 4864 | **红** | 两者都达标，按颜色顺序 |
| 5120 | - | 5200 | 5200 | 4940 | **红** | 差 1.5% 分不出，按颜色顺序 |
| - | 5000 | 5000 | 5000 | 4750 | **绿** | 并列，绿在蓝前 |
| 5000 | 4950 | 4900 | 5000 | 4750 | **红** | 三者都达标，按颜色顺序 |
| - | - | - | 0 | — | **不抓** | 一个都没有 |

### 7.3 抓取状态机

**绝对不要写成"收到有效帧就抓"。**

```
IDLE ──连续3帧同一目标──→ ALIGNING ──到位──→ GRASPING ──夹紧──→ LIFTING ──→ PLACING ──→ IDLE
                              ↑                                                    │
                              └──────── 抓取全程忽略新目标 ────────────────────────┘
```

关键点：
- **抓取过程中一律不看视觉数据**，只在 `IDLE` 状态采纳
- 目标连续 3 帧有效才启动，单帧不动作
- 抓完回到 `IDLE`，木块已从画面消失，`pick_target()` 会自动选下一块

### 7.4 抓失败怎么办

木块还在画面里 → 该槽位仍然有效 → 会再次被选中。
必须加**重试计数**：同一个槽位连续失败 3 次就跳过，否则会死磕一块永远抓不到的木块。

## 8. 像素坐标 ≠ 机械臂坐标

这是最容易踩的坑，务必和队友讲清楚。

**像素坐标不能直接当舵机角度用。** 中间差着两次变换：

1. **相机内参**：像素 → 相机坐标系下的角度
2. **手眼标定**：相机坐标系 → 机械臂基座坐标系

而且：
- 木块有高度，桌面上的点和平面的映射不是简单线性
- **云台一转，之前的映射全部失效**，必须带上 `pan/tilt` 重新算
- 摄像头是**装在机械臂上**的，机械臂一动，视角也跟着动

**第一版建议**：不要做完整的坐标换算。用"**固定观察姿态 + 分区域抓取**"——
把工作区切成 3×3 九宫格，每个格子对应一套事先调好的舵机角度，看到木块落在哪个格子就执行哪套动作。

这样精度够用、代码简单，答辩时也讲得清楚。等这版跑稳了，再考虑做真正的手眼标定。

### 8.1 坐标有保质期 —— 摄像头装在夹爪上的后果

摄像头和夹爪是一体的，这是 **eye-in-hand** 构型。它带来一个必须理解的性质：

> **这一帧的坐标，只在拍这一帧的那个姿态下有效。**

机械臂一动，同一块木块的像素坐标立刻变了。所以协议传的是**瞬时观测**，不是**世界坐标**。
由此推出两条铁律：

1. **只有机械臂静止时才读坐标。** 运动期间收到的帧必须整帧丢弃，不是"参考一下"。
2. **进对准阶段前把目标锁死。** 不要每帧重新决策，否则木块抖一下目标就换，机械臂会来回摆。

好消息是 eye-in-hand 有个天然优势：**摄像头大致和夹爪同轴**。
「让木块移到画面中心」≈「夹爪对准木块」，这比「像素 → 毫米 → 逆运动学」简单得多，
不需要精确标定相机内参。

代价是夹爪下降时木块会移出画面（太近、失焦），**最后一段必须开环**。
所以完整流程是：视觉负责"送到上方"，开环负责"下降、闭合、抬升"。

### 8.2 延迟分布 —— 瓶颈不在通信

从「木块出现在画面里」到「STM32 拿到坐标」：

| 环节 | 耗时 | 占比 |
| --- | --- | --- |
| 曝光 + 采集（30 FPS） | ~33 ms | 11% |
| 三色 `find_blobs` | ~15~25 ms | 6% |
| **稳定判定（5 帧 / 250 ms）** | **250 ms** | **80%** |
| 串口传输（55 字节 @ 115200） | ~5 ms | 2% |
| STM32 解析 | < 1 ms | <1% |
| **合计** | **~310 ms** | |

**通信只占 5 ms。** 改波特率、压缩协议格式、换二进制编码，最多省下 4 ms，
对总延迟毫无意义。真要提高响应速度只有两条路：

- 调低 `STABLE_FRAMES` / `STABLE_MS`（代价：误判变多）
- 用 `color_detection.py` 里的 `TRACK_MODE`（2 帧 / 60 ms / 发送间隔 50 ms）

`TRACK_MODE` 下总延迟降到约 **100 ms**，够做慢速视觉伺服，但坐标抖动明显更大，
**不能用来做最终夹取判定**。

**仿真实测**（30 FPS、±3 像素噪声）：

| 场景 | `SEARCH` | `TRACK` |
| --- | --- | --- |
| 静止，首次出结果 | 317 ms | **119 ms** |
| 静止，坐标抖动 | 2.04 px | 2.02 px |
| 移动 1 px/帧，有效帧 | 49/120 | 110/120 |
| 移动 2 px/帧，有效帧 | **3/120** | 100/120 |
| 移动 3 px/帧，有效帧 | **0/120（锁不住）** | 92/120 |
| 移动 5 px/帧，有效帧 | 0/120 | 76/120 |

**关键结论：`SEARCH` 模式在目标移动超过 2 px/帧时完全失效。** 机械臂一动就必须切 `TRACK`，
否则 STM32 收到的全是 `-1,-1,0`，表现为「一启动就丢目标」。

### 8.3 三种定位方案对比

| 方案 | 需要标定什么 | 精度 | 工作量 | 适合阶段 |
| --- | --- | --- | --- | --- |
| **A. 固定观察姿态 + 九宫格查表** | 9 个格子的舵机角度 | 中（格子内靠固定动作） | 低 | 第一版，推荐 |
| **B. 视觉伺服（边走边调）** | 像素偏差 → 舵机增量的符号和增益 | 高 | 中 | 第二版 |
| **C. 完整手眼标定** | 相机内参 + 手眼矩阵 + 逆运动学 | 最高 | 很高 | 不建议课程设计做 |

方案 A 的问题：木块落在格子边界时会有跳变，且格子内位置精度取决于格子大小。
方案 B 能解决这个问题，但需要闭环控制，调不好会震荡。

**建议：先用 A 把整个流程跑通、能演示，再考虑把 A 的最后一公里换成 B。**

## 9. 调试方法

### 9.1 不接 STM32 也能验证

`color_detection.py` 里把 `UART_ENABLED = False`，帧内容会打印到 CanMV IDE 的终端：

```
@T,42,90,90,320,240,5120,-1,-1,0,-1,-1,0*53
```

**先在这里确认格式、数字、校验都对，再去接线。** 顺序反了会很痛苦：识别不准 + 串口不通两个变量搅在一起，根本分不清哪边的锅。

### 9.2 接 STM32 后

- 用 USB-TTL 模块并接到 PA2/PA3 上，电脑串口助手 115200 8N1 看原始字节
- 或者用 STM32 的另一个串口（USART1 如果空着）打印解析结果
- 校验不过时，先把收到的原始字符串打印出来，逐字节对

### 9.3 常见故障对照

| 现象 | 最可能的原因 |
|---|---|
| 一个字节都收不到 | TX/RX 接反了；或者 GND 没接 |
| 全是乱码 | 波特率不对；或 GND 没接 |
| 偶尔收到半帧 | 拼帧逻辑没写，直接在主循环读 DR |
| 校验永远不过 | 把 `@` 或 `*` 算进校验了 |
| 数据对但机械臂乱动 | 没做新鲜度超时，在用陈旧坐标 |
| 抓到一半又重抓同一块 | 抓取状态机没锁，`IDLE` 判断漏了 |
